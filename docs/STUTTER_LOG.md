# 自动卡顿记录

原生游戏默认自动记录，无菜单入口，不截图、不上传，也不记录玩家姓名、网络地址或存档内容。headless、Web 和 `--automation` 检查默认关闭记录；专项通过合成帧及后台文件写入验证行为，不代表实际 GPU 性能验收。

## 文件位置

Windows 文件资源管理器地址栏输入：

```text
%APPDATA%\Godot\app_userdata\Undead Survivor · Godot\diagnostics\stutter
```

这是 `user://diagnostics/stutter`，独立于 EXE 解压目录和存档槽。只有检测到异常并完成收集后才创建目录和报告；没有此目录不代表功能失效。每次异常生成同名 `stutter_日期_时间_运行时间.json` 和 `.txt`，保留最近20组。把对应两份文件一并提供即可分析。

## 触发和开销

- 内存环形缓冲最多2048帧，记录帧间实际时间、逻辑/物理/视图更新、寻路、敌人网格构建与节点创建/销毁请求、存档及主机快照发送的次数、累计和最大耗时；附带波数、存活数、待出怪数、模式、人数、画质、节点数和静态内存。
- 活跃游戏中单帧达到100ms（或限帧目标的3倍，取较大值），或一秒内至少3帧达到40ms（或目标的1.8倍，取较大值）时触发。正常30FPS限帧、暂停和失焦不触发。
- 捕获异常前约5秒，持续收集至恢复后约3秒；连续异常合并，触发后最多10秒或2048帧结束一份记录。高帧率/极端长停顿下可用历史受容量限制。
- 收集完毕后由后台线程生成摘要、写盘并轮换旧报告。主线程仅收集计时和有界数据；待写队列最多2份，连续异常报告之间至少间隔5秒。正常游戏不等待磁盘。退出时完成剩余捕获并等待写入，关进程或崩溃可能丢失尚未写盘的记录。

## 如何解读

TXT 提供峰值帧耗时、超过50/100ms的帧数和各模块计时。JSON 提供逐帧的 `at_us`、`frame_us`、`metrics` 与 `state`，时间是本次运行的单调微秒时间；`wall_time` 是本地系统时间。

| 计时名称 | 含义 |
|---|---|
| physics / logic | 主物理回调 / 权威模拟更新 |
| view_update / enemy_view | 主视图回调 / 敌人视图更新 |
| pathfinding | 实际路径查询，包含直线路径和失败查询 |
| endpoint_lookup / path_astar | 导航起终点修正 / 实际 A* 搜索，均属于嵌套范围 |
| navigation_grid_update | 建筑增减时更新导航阻挡格的 CPU 耗时 |
| mesh_build | 缓存未命中时生成敌人网格 |
| enemy_create / enemy_retire | 敌人表现节点创建 / 请求延迟销毁 |
| save / settings_save | 进度存档 / 设置写入，包含失败尝试 |
| network_snapshot | 房主生成并发送权威世界快照 |

这些范围存在包含关系，例如 logic 包含寻路与部分存档，enemy_view 包含网格构建，不能将所有耗时相加。先在 JSON 中对齐异常帧和耗时突增，再比较相同事件的正常帧。累计耗时高不等于造成某次卡顿。

未测量 GPU 执行、驱动编译、操作系统调度与引擎内部延迟释放；`enemy_retire` 只统计敌人层级销毁请求，不能代表全场节点真正释放耗时。帧间时间显著上升但这些计时都低时，应标为未定位，继续采集原生渲染或系统性能数据。报告是诊断线索，不会自动宣称根因或优化成功。

## 寻路诊断（schema 2）

原文件位置和触发方式不变。逐帧新增 `physics_steps`（该观察区间的主物理回调次数）、`process_frame`、`navigation`；场景状态新增玩家位置、导航版本、待处理与已完成请求数。请求携带引擎过程帧/物理帧编号，可对齐补算、队列和耗时；物理回调计时不覆盖引擎内部全部物理工作。

- `navigation.counts` 完整统计请求用途、原因、结果和事件次数。`requests` 记录起终点坐标、修正后的导航格、投影距离、敌人类型、目标类型、模拟时间、队列等待时间，以及 `direct_us / endpoint_us / astar_us / total_us`。通过调度器执行的请求还记录当时的队列长度和物理步预算使用数；直接调用路径接口的请求没有队列信息。
- `purpose` 区分 `reach`（能否追到玩家）、`move`（实际移动）与 `forest_rejoin`（偏离固定路线后归队）。`reason` 区分首次查询、缓存到期、目标/怪物跨格、目标移动、导航变化、受阻。
- `outcome` 区分直达、完整路线、投影到可走终点、不可达、无有效端点。`projected_endpoint` 不自动意味着错误：玩家可以站在敌人净空边缘，怪物仍可能从攻击距离内命中。
- `events` 记录导航版本变化、移动受阻、林地归队、请求延后和排队结果因目标改变被丢弃；慢端点修正或无效端点也有独立事件。不会记录玩家姓名、Steam 标识、输入录像或存档内容。
- 每帧最多采样2条快速查询；耗时达到2ms的查询优先保留，查询详情总上限16条、事件上限8条。溢出时保留更慢的请求，`dropped_requests / dropped_events` 标明未保存的详情数量；聚合次数仍完整。它们沿用2048帧内存环形缓冲，不逐条同步写盘。
- TXT 增加物理补算峰值、分类计数和最慢5条请求的分段耗时；JSON 摘要列出最慢20条请求。schema 1 的旧记录缺少这些字段，不能据此倒推出旧事件的准确目标位置。

## 2026-10-26 定向排查与修复

基线为 `fb36ce2`。本机只运行原生 headless CPU 检查，手工布置条件、由正式模拟逻辑执行；不是桌面操作、GPU验收或真人试玩。固定1/5/10只普通怪物，对照桥中与贴桥栏位置，移动目标跨格/缓存刷新，门损坏与恢复，以及被移出固定路线后的安全归队。

桥栏边缘可以稳定复现昂贵查询：同样数量，玩家移回桥中后消失。分段计时表明主要热点是 `nearest_cell → endpoint_link`：每个候选格都可能线性扫描整张地图的物理障碍。现使用保留原始物理轮廓的空间索引，只检查相关格内的障碍；候选按距离排序，等距时保留旧的行/列顺序。回归与旧线性判定比较导航格结果，并确认复现位置允许玩家实际站立。

门损坏/恢复另有整图导航格重置开销，现只重置旧/新建筑覆盖区域；仍递增导航版本以失效旧路径。专项将每次局部更新后的整张导航阻挡位图与旧全量重建结果对比，检查门开通、阻挡恢复及其他建筑重叠处理。

`./tools/validate-headless.ps1 -Mode PathStalls` 检查四类条件并输出 `artifacts/path-stalls-validation.json`，包含样本耗时和实际源码 SHA-256。时间仅作观测，不作为容易受系统调度影响的硬断言；通行语义、队列日志和固定容量使用确定性检查。该专项已加入全量/发布流程；日常仍使用基础检查并按需额外执行本专项。已有121/257ms等旧日志的分段数据不足，不能确认每个旧事件都由这两个热点造成，也不宣称所有卡顿已解决。
