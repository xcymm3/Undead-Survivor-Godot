# 自动卡顿记录

原生游戏默认自动记录，无菜单入口，不截图、不上传，也不记录玩家姓名、网络地址或存档内容。headless、Web 和 `--automation` 检查默认关闭记录；专项通过合成帧及后台文件写入验证行为，不代表实际 GPU 性能验收。

## 文件位置

Windows 文件资源管理器地址栏输入：

```text
%APPDATA%\Godot\app_userdata\Undead Survivor · Godot\diagnostics\stutter
```

这是 `user://diagnostics/stutter`，独立于 EXE 解压目录和存档槽。只有检测到异常并完成收集后才创建目录和报告；没有此目录不代表功能失效。每次异常生成同名 `stutter_日期_时间_运行时间.json` 和 `.txt`，保留最近20组。把对应两份文件一并提供即可分析。

## 触发和开销

- 内存环形缓冲最多2048帧，记录帧间实际时间、逻辑/物理/视图更新、寻路、敌人网格构建与节点创建/销毁请求、存档及主机快照发送的次数、累计和最大耗时；附带波数、存活数、待出怪数、模式、人数、画质、节点数和静态内存。
- 活跃游戏中单帧达到100ms（或限帧目标的3倍，取较大值），或一秒内至少3帧达到40ms（或目标的1.8倍，取较大值）时触发。正常30FPS限帧、暂停和失焦不触发。
- 捕获异常前约5秒，持续收集至恢复后约3秒；连续异常合并，触发后最多10秒或2048帧结束一份记录。高帧率/极端长停顿下可用历史受容量限制。
- 收集完毕后由后台线程生成摘要、写盘并轮换旧报告。主线程仅收集计时和有界数据；待写队列最多2份，连续异常报告之间至少间隔5秒。正常游戏不等待磁盘。退出时完成剩余捕获并等待写入，关进程或崩溃可能丢失尚未写盘的记录。

## 如何解读

TXT 提供峰值帧耗时、超过50/100ms的帧数和各模块计时。JSON 提供逐帧的 `at_us`、`frame_us`、`metrics` 与 `state`，时间是本次运行的单调微秒时间；`wall_time` 是本地系统时间。

| 计时名称 | 含义 |
|---|---|
| physics / logic | 主物理回调 / 权威模拟更新 |
| view_update / enemy_view | 主视图回调 / 敌人视图更新 |
| pathfinding | 实际路径查询，包含直线路径和失败查询 |
| mesh_build | 缓存未命中时生成敌人网格 |
| enemy_create / enemy_retire | 敌人表现节点创建 / 请求延迟销毁 |
| save / settings_save | 进度存档 / 设置写入，包含失败尝试 |
| network_snapshot | 房主生成并发送权威世界快照 |

这些范围存在包含关系，例如 logic 包含寻路与部分存档，enemy_view 包含网格构建，不能将所有耗时相加。先在 JSON 中对齐异常帧和耗时突增，再比较相同事件的正常帧。累计耗时高不等于造成某次卡顿。

未测量 GPU 执行、驱动编译、操作系统调度与引擎内部延迟释放；`enemy_retire` 只统计敌人层级销毁请求，不能代表全场节点真正释放耗时。帧间时间显著上升但这些计时都低时，应标为未定位，继续采集原生渲染或系统性能数据。报告是诊断线索，不会自动宣称根因或优化成功。
